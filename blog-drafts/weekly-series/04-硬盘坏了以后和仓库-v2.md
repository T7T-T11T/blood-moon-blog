硬盘坏掉之前，我知道 GitHub 很重要。

我知道项目最好推到仓库里，知道代码不能只放在桌面，知道数据和文档最好也备份。但这些“知道”，和真的经历一次东西不在了，完全不是一回事。

那次本地项目回到很早的版本时，我是真的有一种被打了一闷棍的感觉。

不是说所有东西都彻底蒸发了。云端还留着一些数据，项目目录里也不是完全空白。但你会发现，最难受的不是少了一两个文件，而是你突然不知道：哪个版本才是最新的？以前改过什么？现在还能不能继续用？那些我当时以为“肯定在电脑里”的东西，到底去了哪里？

那种感觉很难受。

因为项目不是只有代码。里面还有你做过的决定、没来得及整理的文档、临时改过的配置、这次为什么这么写、上次为什么没那么写。代码回去了，很多上下文也跟着断了。

## 我后来才明白：本地不是仓库，本地只是工作台

以前我会把电脑当成项目的家。现在我更愿意把它看成工作台。

工作台当然重要，我每天都在上面写东西。但它不该是唯一的地方。硬盘会坏，系统会重装，文件会误删，甚至有时候你只是换了一台电脑，就会发现自己忘记了好多东西。

现在我做项目会慢慢养成一个习惯：有一个能跑的阶段，就提交；有一次重要修改，就写清楚；项目哪怕刚起步，也先建仓库。

所以我的 GitHub 上现在多了几个看起来还很空的仓库。

以前我可能会觉得，空仓库有什么好传的，等做得像样一点再说。现在我的想法反过来了：**先让它有个能回去的地方。** 哪怕里面现在只有 README，哪怕功能还没开始写，至少这个项目不是只活在我这台电脑上。

![我的博客仓库卡片](https://opengraph.githubassets.com/1/T7T-T11T/blood-moon-blog)

目前已经公开的博客项目在这里：[blood-moon-blog](https://github.com/T7T-T11T/blood-moon-blog)。它不只是一个展示页面，仓库里还留着前端、后端、数据库迁移、测试和部署说明。我的 GitHub 主页也在这里：[T7T-T11T](https://github.com/T7T-T11T)。

我不准备把所有仓库都塞进文章里。有些是私人内容，有些只是刚建起来的空项目，没有必要为了“看起来多”就摆出来。但我想留下这个链接，是因为它确实是这次教训之后的一个变化：我开始让项目有历史、有去处。

## Emoji 说的恢复，让我明白“代码回来”还不够

小程序恢复时，我一开始最想做的当然是把页面弄回来。

后来才发现，光有页面没有用。旧用户的数据还在不在？旧作品能不能继续显示？云端的函数是不是现在这版需要的？不同历史字段怎么兼容？图片要怎么让别的账号也能看见？

这些问题不会因为你把项目文件夹找回来了就自动消失。

所以后来我做的不只是修代码，还去核对真实的云端数据和功能；把旧字段兼容到新逻辑里；把部署步骤、真机验收、维护注意事项写成文档。这个过程很慢，也不如“重新做一个新功能”有成就感，但它让我终于能比较安心地说：这不是一个空壳的新版本，它接住了以前留下来的东西。

## 我现在给自己留的底线

- 代码要有 Git 历史；
- 项目要有远程仓库，不只在本地；
- 重要数据要有导出或备份；
- 部署和恢复不能只写在脑子里；
- 每次做完一个阶段，留一段人能看懂的记录。

这不代表我以后就不会丢东西，也不代表我已经很专业了。

只是我不想再经历一次那种感觉：电脑出事以后，站在一堆不完整的文件面前，连自己曾经做到哪里都不知道。

硬盘坏掉给我的打击挺大。但现在回头看，它也逼着我开始认真对待“保存”这件事。

项目做出来很重要。让它能活下来，也一样重要。
