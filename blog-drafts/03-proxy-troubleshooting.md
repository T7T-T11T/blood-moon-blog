“浏览器能打开网页，但某些程序就是上不了网。”

这句话很容易把人带进一个很长的排查清单：DNS、路由、防火墙、网卡驱动、IPv4/IPv6、系统代理、网络重置……它们都值得检查，但这次问题的根因不在这些大方向里，而藏在一个更小、更容易被忽略的地方：用户级代理环境变量。

## 现象为什么容易误导人

问题出现时，浏览器访问网页正常，但加速器、VPN 客户端和命令行联网测试却失败了。换网络、甚至换手机热点后，症状仍然存在。

这几个现象组合起来其实已经给了一个很重要的提示：

- 基础网络链路大概率没完全断；
- 问题不像是某一个 Wi-Fi、路由器或 DNS 服务单独失效；
- 异常会跟着这台电脑和部分程序走。

当“有的程序能上网、有的不能”时，与其立刻重置整个网络，不如先问一句：**这些程序是不是在使用不同的代理来源？**

## 关键突破：独立测试暴露了本地代理

浏览器的网络路径比较复杂：它可能使用自己的配置、系统代理、已有连接或扩展。为了避免被浏览器现象误导，可以用一个独立的网络工具做测试。

```powershell
curl.exe -I https://www.microsoft.com
```

这次的报错信息里出现了类似 “over proxy 127.0.0.1” 的提示。它说明请求没有直接发往互联网，而是先被送到本机某个端口。进一步定位后，发现代理地址指向一个并未正常服务的本地 SOCKS5 端口。

换句话说，不是网络本身不通，而是部分程序被要求先经过一扇已经关上的门。

## 根因：程序继承了失效的代理变量

Windows 的用户环境变量里可以保存 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 这类设置。许多命令行工具、Electron 应用和网络库在启动时会自动读取它们。

如果这些变量还指向已停止的本地代理，例如 `127.0.0.1` 上一个没有监听的端口，程序会把所有请求交给这个失效代理，表现出来就是“它自己无法联网”。而浏览器因为没有走同一条路径，仍然可能正常。

这也解释了为什么网络重置、切换热点、检查网卡都没有彻底解决问题：它们没有触及每个新进程继承到的用户级配置。

## 一分钟排查顺序

下次遇到相似情况，我会按下面这个顺序检查，先缩小范围，再决定是否做更大的操作。

### 1. 查看当前会话的代理变量

```powershell
Get-ChildItem Env:*_PROXY
```

### 2. 查看用户级持久变量

```powershell
Get-ItemProperty 'HKCU:\Environment' |
  Select-Object HTTP_PROXY, HTTPS_PROXY, ALL_PROXY
```

### 3. 比较直连与默认请求

```powershell
curl.exe -I https://www.microsoft.com
curl.exe --noproxy "*" -I https://www.microsoft.com
```

如果默认请求失败，而明确绕过代理后成功，就应优先检查残留的代理设置。

### 4. 确认本地端口是否真的有服务

```powershell
Get-NetTCPConnection -LocalPort <代理端口> -State Listen -ErrorAction SilentlyContinue
```

没有监听程序的本地端口，不应该被设置为全局出口。

## 修复时需要注意的两件事

第一，清除持久变量后，已经打开的程序不会自动忘掉旧值。环境变量通常在进程启动时继承，所以需要完全退出并重新打开受影响的软件；必要时注销或重启系统。

第二，不要一开始就做不可逆或范围很大的网络重置。网络重置也许能解决某些问题，但会增加变量，丢失现有配置，还可能掩盖真正的原因。先用小范围、可验证的测试定位，效率更高，也更容易把经验复用到下一次。

## 这次排障真正留下的不是一条命令

这件事最有用的收获，是一个判断框架：

> 当浏览器正常、部分程序异常，而且换网络仍无效时，优先检查进程级、用户级的代理与环境变量。

网络问题经常看起来像“整台电脑坏了”，但很多时候只是某个应用层配置仍停留在过去。先看谁在走哪条路，再决定动哪里，往往比把所有开关都试一遍更快。
