# 博客首页为什么加载了后台编辑器

之前检查博客的构建产物，发现首页要加载的 JS 比预想大。读者只是进来看文章，后台编辑器和代码高亮的依赖却也跟着进来了。

翻了一遍配置，主要改了两处：Element Plus 的引入方式，以及 `manualChunks` 的分包规则。

## 先处理组件库

最初是在入口里全局注册 Element Plus：

```js
import ElementPlus from 'element-plus';
app.use(ElementPlus);
```

当时的构建产物里能搜到 `ElTour`、`ElCascader`、`ElCalendar`，但项目没有用这些组件。删掉全局注册后，还检查了 `ElMessage` 这类在脚本里调用的组件。

旧记录里做过两种导入方式的对比：

```js
import { ElMessage } from 'element-plus';

// 对照：直接从组件目录导入
import { ElMessage } from 'element-plus/es/components/message/index.mjs';
```

在那次构建环境里，组件路径导入得到的包更小。后来配置了自动引入插件，用自定义 resolver 把组件映射到各自的入口。这是这个项目当时的处理方式；是否需要这样改，还是得看具体版本和构建结果，不能只凭一行 import 判断。

写 resolver 时还碰到了子组件的入口问题。有些组件由父包导出，需要另外映射：

| 组件 | 导出位置 |
| --- | --- |
| `ElFormItem` | `form` |
| `ElOption`、`ElOptionGroup` | `select` |
| `ElTabPane` | `tabs` |
| `ElTableColumn` | `table` |
| `ElSubMenu`、`ElMenuItem` | `menu` |

没处理这些映射时，构建会报找不到导入路径。当前配置里的 `nestedParent` 就是处理这件事的。

## 后台依赖怎么进了首页

另一个问题在 `manualChunks`。当时用 `return 'vendor'` 兜底，把没单独分组的第三方依赖全塞进一个包。

首页需要 axios，所以要加载这个包。但编辑器用的 ProseMirror、高亮库等也被塞在里面，结果一起下载了。路由虽然写了懒加载，手动分包又把它们合到了一起。

后来去掉兜底，只对几个大依赖单独分组，其余交给构建工具处理：

```js
manualChunks(id) {
  if (id.includes('node_modules')) {
    if (id.includes('echarts')) return 'vendor-echarts';
    if (id.includes('@element-plus/icons-vue')) return 'vendor-icons';
    if (id.includes('element-plus')) return 'vendor-element';
    if (
      id.includes('vue-router') || id.includes('pinia') ||
      id.includes('@vue/') || id.includes('node_modules/vue/')
    ) {
      return 'vendor-vue';
    }
  }
}
```

改完再看，编辑器和高亮相关代码才留在对应的路由包里。这里要检查的是首页实际请求了哪些文件，单看构建目录的总体积，分不清哪些会在首屏加载。

## 当时留下的体积记录

原来的优化记录写的是下面这组数，作为那次改动的对比保留。它不是现在生产版本重新测出来的数据，后续功能和依赖变化都可能影响结果。

| 项目 | 优化前 | 优化后 |
| --- | --- | --- |
| 首屏 JS，压缩后未 gzip | 约 2,000 KB | 约 680 KB |
| 首屏 JS，gzip 后 | 约 800 KB | 约 230 KB |
| 编辑器和高亮依赖 | 随首屏加载 | 编辑页加载 |
| Element Plus CSS | 整包引入 | 按组件引入 |

没有把构建目录里所有包都加进首屏体积，后台统计页的 ECharts 等需要另外看。传输体积也不等于加载耗时，旧记录没有保留可复查的测速材料，所以这里不写快了多少秒。

这次最费时间的地方，就是明明写了懒加载，首页还是在下载不需要的东西。以后改分包配置，我会连着实际请求一起看，不能只看文件名像是已经拆好了。
